# Implementation Plan: Gateway Core (Auth + Chat)

**Branch**: `002-gateway-core` | **Date**: 2026-08-29 | **Spec**: `specs/002-gateway-core/spec.md`

## Summary

Build the NestJS gateway's first real slice: user accounts with JWT auth,
a Prisma-backed Postgres schema (users, refresh tokens, messages, usage
log), rate limiting + daily quota, a health check, and the chat SSE
pipeline (intent-extraction call → deterministic branch or streamed chat
call) against the local Ollama server set up in Feature 001.

## Technical Context

**Language/Version**: TypeScript, Node.js 24 (matches installed runtime)

**Primary Dependencies**: NestJS 10, Prisma 5, `@nestjs/jwt` + `@nestjs/passport` (JWT strategy), `argon2` (password hashing), `@nestjs/throttler` (rate limiting), `@nestjs/swagger` (OpenAPI), `openai` SDK (pointed at Ollama's compatible endpoint)

**Storage**: PostgreSQL (`botvy` database, from Feature 001) via Prisma

**Testing**: Vitest — unit tests for intent-branch logic, quota calculation, refresh-token rotation; no e2e harness yet (manual curl verification per spec's acceptance scenarios, matching Feature 001's approach)

**Target Platform**: Linux container (Docker), joins the `infra/docker-compose.yml` stack from Feature 001 as a new `gateway` service

**Project Type**: Web backend (single NestJS app) inside the `apps/gateway` workspace package

**Performance Goals**: Deferred to Feature 001's open item (CUDA/driver blocker) — this feature verifies pipeline correctness, not throughput

**Constraints**: Single writer to Postgres (constitution Principle I); JWT access token short-lived, refresh token rotating with reuse detection; every route except `/health` requires auth

**Scale/Scope**: Multi-user from the first migration (constitution Principle VI) — no singleton assumptions anywhere in the schema

## Constitution Check

*GATE: Must pass before Phase 0 research. Re-check after Phase 1 design.*

- **I. Gateway Owns All Data** — satisfied: this feature *is* the gateway; Prisma is its only DB client, and no other service in the compose stack is granted DB credentials.
- **II. n8n Is Workflow Infrastructure Only** — N/A this feature (n8n workflows arrive in the Reminders feature); nothing here changes n8n.
- **III. Local-First LLM** — satisfied: the `openai` client's `baseURL` points at `http://host.docker.internal:11434/v1` (Ollama), never a cloud endpoint; no API key configuration for a cloud provider exists in this feature.
- **IV. Forward-Only Migrations** — satisfied: `prisma migrate dev` generates the initial migration; no existing migration is ever hand-edited once committed.
- **V. Single Public Surface** — satisfied: the gateway is the one service this whole system intends to expose publicly (via Feature 001's tunnel, retargeted from the placeholder to this service by end of this feature).
- **VI. Multi-User By Default** — satisfied: every table keys off `userId`; message history and usage log are queried filtered by the authenticated user, verified explicitly by acceptance scenario SC-001.
- **VII. Test-Then-Verify** — satisfied: vitest unit tests for quota/intent/refresh-rotation logic; every acceptance scenario has a corresponding manual curl verification captured in tasks.md before being marked done.
- **VIII. YAGNI** — satisfied: no OAuth/SSO, no password reset, no email verification, no admin-elevation UI — all explicitly deferred per spec's Assumptions; e2e test harness deferred until enough surface exists to justify it over manual curl checks.

No violations. Complexity Tracking table not needed.
